# 固定输出格式规范

本文件规定本 skill 对外交付时的固定格式：事实核对卡、文件命名与输出目录、交付报告。所有生成活动都遵守本文件；用户或通知明确指定命名、目录或输出形式时，以用户或通知为准。

## 1. 事实核对卡（生成前输出）

确认必要信息后、开始成稿前，先向用户输出一次事实核对卡。核对卡是所有交付物的统一事实源，案例、总结表、心得体会和 PPT 不得与其冲突。

```markdown
| 项目 | 内容 | 来源 |
|---|---|---|
| 活动主题 | （主题全称，含口号） | 通知/用户 |
| 活动名称 | 主题 + 主题团日活动 | 生成规则 |
| 学院（全称） | | 通知/用户 |
| 团支部（简称） | | 用户 |
| 日期口径 | 单日 2026年6月18日 或 跨天区间 | 用户 |
| 活动地点 | | 通知/用户 |
| 支部人数 / 参加人数 | 数字，或「未涉及」「待确认」 | 用户/授权生成 |
| 负责人 / 联系电话 | 仅总结表需要时填写 | 用户 |
| 文风口径 | 已开展（过去时）或 方案（拟/计划） | 用户语义 |
| 篇幅口径 | 案例 1800—2800 字 / 心得 800—1200 字 / PPT 10—12 页 | 默认或用户指定 |
| 本次交付物 | 案例docx、总结表docx、心得docx、PPT提示词md | 用户要求 |
```

- 未确认字段写「待确认」，不得虚构；字段只在本批交付物需要时才要求确认。
- 用户修改核对卡后，先更新核对卡再生成，全程保持单一事实源。
- 一次生成多种材料只输出一张核对卡；分多轮追加材料时复用并更新同一张核对卡，不重复输出全表。

## 2. 文件命名与输出目录

**输出根目录**固定为 `E:\cc项目\团日活动材料\`（本 skill 根目录同级），全部交付件、模板副本、内部中间目录和 PPT 生成项目目录都落在其中。三条硬约束：

1. **不得位于本 skill 目录内部**——交付件会被算进 skill 包体，影响打包与安装（包体上限为 2000 个文件、未压缩总量 100 MB）。
2. **不得位于 C 盘**，含系统临时目录；脚本的中间产物写在输出目录内的子目录，不使用系统临时目录的默认位置。
3. 用户明确指定目录时以用户目录为准，但同样不得违反第 1、2 条。

模板副本写入输出目录，不覆盖 `assets/` 原模板。

| 交付物 | 默认文件名 |
|---|---|
| 活动案例 | `{支部前缀}-活动案例-{YYYYMMDD}.docx` |
| 总结表 | `{支部前缀}-活动总结表-{YYYYMMDD}.docx` |
| 心得体会（第 1 份 / 第 2 份） | `{支部前缀}-心得体会-1-{YYYYMMDD}.docx` / `{支部前缀}-心得体会-2-{YYYYMMDD}.docx` |
| PPT | `{支部前缀}-团日活动PPT-{YYYYMMDD}.pptx` |

示例（命名前缀为 `软件2450`、活动日期 2026年6月18日）：

```
软件2450-活动案例-20260618.docx
软件2450-活动总结表-20260618.docx
软件2450-心得体会-1-20260618.docx
软件2450-心得体会-2-20260618.docx
软件2450-团日活动PPT-20260618.pptx
```

- `{支部前缀}` 由用户提供的命名前缀决定，形如 `软件2450`，写在文件名最前；心得默认 2 份，用 `-1`、`-2` 区分。
- `{YYYYMMDD}` 使用确认后的活动日期；日期未确认时省略该段。
- 预览版在扩展名前加 `-预览`，例如 `软件2450-活动总结表-预览.docx`。
- 支部前缀缺失时用学院简称，再缺失时用「团日活动」。
- 文件名不出现空格、`[待补]` 等占位符。

### 2.1 输出目录内的内部目录

输出目录下有两个内部目录，属于生成过程的中间产物，**不计入交付清单**：

| 目录 | 内容 | 是否交付 |
|---|---|---|
| `_source/` | 生成 DOCX 用的输入 JSON（`case.json` / `table.json` / `reflection.json`） | 否，保留以便复现与回溯 |
| `_preview/` | `render_preview.py` 产出的 PDF 与逐页 PNG | 否，仅供交付前目视检查 |

交付清单只列最终的 DOCX 和 PPTX；内部目录不作为交付物上报，其内容也不得混入正式材料的正文。用户明确要求交付中间文件时才列出。

## 3. 交付报告（交付后输出）

每次交付文件后，输出以下固定结构的交付报告：

```markdown
## 交付清单
| 文件 | 类型 | 版式检查 |
|---|---|---|
| 软件2450-活动案例-20260618.docx | 活动案例 | 已渲染检查 |
| 软件2450-活动总结表-20260618.docx | 总结表 | 已渲染检查 |
| 软件2450-心得体会-1-20260618.docx | 心得体会 | 已渲染检查 |
| 软件2450-心得体会-2-20260618.docx | 心得体会 | 已渲染检查 |
| 软件2450-团日活动PPT-20260618.pptx | PPT（含演讲备注） | 引擎质检通过 + 已渲染检查 |

## 事实核对
- 主题：……（各材料一致）
- 日期口径：……
- 地点：……
- 人数：…… / 本批材料未涉及
- 主要流程：……

## QA 结果
逐项对应 generation-spec 交付前 QA 清单，标注「通过」或「不适用」。

## 待确认事项
- 无，或列出仍缺失、需用户确认的字段。
```

- 只交付纯文本（如心得体会正文）时，交付报告可以与正文合并为一段简洁说明，但事实核对五项（主题、日期口径、地点、人数、主要流程）不得省略。
- 版式检查未执行时如实注明原因，不虚构「已检查」。
