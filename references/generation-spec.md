# 团日活动材料生成规格

## 1. 通知解析与事实分层

读取 Word 通知的标题、正文、表格和附件说明，先整理内部事实表，再写材料。事实表至少包含：

| 类别 | 内容 |
|---|---|
| 主题 | 活动主题、口号、核心价值 |
| 背景目标 | 开展原因、面向问题、希望形成的认识或行动 |
| 时间地点对象 | 活动日期口径、地点、对象、是否分批或跨天 |
| 形式内容 | 学习、观影、分享、竞赛、模拟、实践、创作等 |
| 材料要求 | 案例、总结表、心得、PPT、作品和通知要求的附件 |
| 管理要求 | 截止时间、照片规格、命名、邮箱、系统录入等 |
| 缺口冲突 | 模板字段缺口，以及通知与模板之间的矛盾 |

把信息分为五层：

1. **用户/通知已确认事实**：可以直接写入正式材料；
2. **用户授权生成字段**：用户明确允许合理填写的支部人数、参加人数；
3. **合理生成内容**：依据主题和通知构造的过程、互动、讨论、一般氛围和一般成效；
4. **必须询问的事实**：负责人、联系电话等真实身份数据，以及用户指定的日期口径；
5. **材料管理信息**：提交、照片、截止时间、文件名和系统操作，单独记录，不混入活动叙事。

## 2. 问询与写作口径

### 2.1 按交付物最小问询

| 用户要生成的内容 | 必要确认项 |
|---|---|
| PPT | 主题、通知重点、学院/受众、日期口径和特殊要求；页数未指定时默认 10—12 页 |
| 活动案例 | 主题、学院/支部身份、通知重点、是否按已开展语气；字数未指定时默认 1800—2800 字左右 |
| 正式总结表 | 举办支部、负责人、联系电话、活动日期、地点；支部人数和参加人数由用户提供，或在用户明确授权时合理生成 |
| 心得体会 | 是否按已开展活动写；字数未指定时默认 800—1200 字；需要署名或个性化作者信息时再问姓名、班级/支部 |

通知已明确的学院、地点、对象和活动形式不重复询问。不要因为用户只要 PPT 或活动案例，就追问负责人、联系电话、支部人数等总结表专用字段。

### 2.2 人数处理与一致性

- 用户给出支部人数、参加人数时，必须原样使用，不擅自调整、四舍五入或另造一组数字。
- 用户明确说“人数你自己填合理点”“支部人数和参加人数你来定”等，允许合理生成支部人数和参加人数；参加人数不得超过支部人数，数字应保持简洁、自然，不延伸生成姓名、电话或其他身份信息。
- 用户未提供人数且未授权生成时，只在正式总结表确实需要填写时询问；单独生成 PPT、活动案例或心得体会时，不为了填表而追问人数，也不要在正文硬塞精确数字。
- 已确认或授权生成的人数作为统一事实源，案例、总结表、心得体会和 PPT 中出现人数时必须完全一致。

### 2.3 材料一致性

生成前先固定本次活动的主题、日期、地点、人数和主要流程。所有交付物都从这组信息展开：案例可以详细叙述，活动总结表可以压缩，心得可以转为第一人称，PPT 可以转为页面提示，但不得改变事实或另造活动环节。若案例采用知识问答，PPT 应围绕同一环节呈现；若通知没有辩论或作品展示，不得为了凑页面机械添加。

### 2.4 日期处理

- 用户明确说“实际活动时间是 6 月 18 日”：统一写为用户确认的完整日期，例如 `2026年6月18日`。
- 用户明确说“活动就是 6 月 15 日至 6 月 21 日分多天进行”：允许使用该时间段，并按用户说明组织过程。
- 只有通知给出时间段、用户没有说明实际口径时，询问一次：“实际活动是在哪一天举行的？如果确实是跨多天开展，也可以直接使用通知中的时间段。”
- 不擅自把跨天活动改成单日，也不把材料提交截止时间当作活动日期。确认后的日期口径在案例、总结表、心得体会和 PPT 中保持一致。

### 2.5 已开展与方案语气

用户说“按已经开展写”“活动已经办完了”“帮我把过程编完整”“过程你自己编”“活动过程你自己合理生成”“写真实一点”或同义表达时，统一使用过去时：活动开始后、随后、在讨论环节、活动最后、通过此次活动等。只有用户明确要求方案、预览或说明尚未开展时，才使用拟、计划、建议。

## 3. 合理补全规则

允许根据主题、通知形式和校园语境合理构造：

- 活动准备、主持开场、理论学习、视频/材料观看、主题讲解；
- 小组讨论、知识问答、情景模拟、互动活动、代表交流；
- 手抄报、征文、海报、短视频或其他主题作品创作与展示；
- 总结发言、行动承诺、后续宣传、普通活动氛围和一般性活动成效。

可使用自然的材料表达，例如：

> 活动开始后，主持人首先围绕主题进行导入，随后组织支部成员开展相关知识学习。

> 在小组讨论环节，同学们结合校园生活中的实际场景交流自己的认识，并提出相应的防范和行动建议。

> 通过此次活动，支部成员进一步深化了对相关主题的理解，增强了责任意识和行动意识。

这类内容是活动材料的合理补全，不需要用户提供逐项现场记录。补全时要让各环节前后有因果关系，并始终围绕当前通知主题；不能把不存在的精确证据写成事实。

不得自行编造：真实姓名、手机号、身份证号、教师或领导姓名、公章、签名、证书编号、官方获奖结果、无依据的精确统计数据、无来源的具体法律条文、冒充真实来源的新闻案例、个人原话和具体现场数据。可以写一般性效果，不写“某人获得一等奖”“现场有 30 人一致表示……”等证据性句子，除非用户明确提供。

## 4. 活动案例

继续使用 `assets/活动案例模板.docx`，保留模板的附件编号和章节结构。正文推荐 1800—2800 字，但用户要求精简或扩展时服从用户要求。案例身份行严格使用：

`XX学院（全称）  XX团支部（简称）`

正文结构固定为：

### 一、活动策划

写背景、主题理解、活动目标、参与对象、内容设计、活动原则和预期效果。把主题与学院专业、学生特点和校园生活联系起来，使用当前通知提供的内容，不套用其他活动主题。

### 二、组织实施

#### （一）活动准备

写通知传达、材料准备、场地设备、团组织标志、主持衔接、秩序安排和参与方式。负责人、工作人员等未提供的真实身份字段不在案例正文中硬填；用户提供或授权生成的人数如需出现，必须使用统一事实源。

#### （二）活动开展

按照通知安排写主题导入、学习/观看、讲解、讨论、问答、情景模拟、互动、作品创作或其他实际环节。每个环节说明活动目的、参与方式、讨论问题和行动产出；若用户明确已开展，全部使用过去时，并允许合理补全过程细节。

#### （三）活动总结

写成员认识变化、行动转化、支部交流、主题成果和后续计划。一般性成效可以生成，但不虚构精确数据、获奖、领导评价或照片事实。

### 三、案例点评

严格沿用模板的两个小节：

#### （一）案例推广价值

围绕本次活动的环节衔接、主题联系、参与机制和可复制方法，说明推广价值。

#### （二）思考与建议

评论本次活动本身的亮点、不足和改进建议，不能写成与活动无关的材料提交提醒。

### 模板占位与注释行处理

生成副本时必须完成占位清理，保持交付件规范：

- 主标题「XXXX团日活动案例」替换为实际活动标题；
- 删除模板中所有排版说明注释行（如「（标题字体为宋体……）」「注：一级标题字体……」「（注：此部分需说明……）」）；
- 保留「附件3：」编号行和两段式身份行；
- 正式交付件中不保留「（模板）」字样。

## 5. 总结表

继续使用 `assets/团日活动总结表（团支部）.docx`，不重新制作表格，不改变合并单元格和列宽行高。

| 字段 | 生成规则 |
|---|---|
| 学院名称 | 使用通知或用户提供的学院全称 |
| 举办支部 | 使用用户提供的团支部/班级；缺少时询问，预览时留空 |
| 活动名称 | 主题 + 主题团日活动 |
| 活动时间、地点 | 使用用户确认的单日或跨天日期口径和地点 |
| 支部人数、参加人数 | 用户提供时原样使用；用户明确授权合理生成时，生成一组参加人数不超过支部人数的数字并在所有材料统一；未提供且未授权时询问，预览时留空 |
| 活动负责人、联系电话 | 只使用用户提供的真实信息；缺少时询问，预览时留空 |
| 活动过程及效果 | 根据通知和活动案例压缩生成，活动过程和一般性效果允许合理补全，但不得改变案例的主要流程或人数 |
| 学院团委意见 | 保留空白、盖章和日期区域 |
| 备注 | 只写必要的材料管理信息或来源冲突 |

正式总结表字段中不出现 `[待补]`；预览版未知字段保持空白。照片、邮箱、系统录入和截止时间不自动写入过程及效果。

## 6. 心得体会/读后感

默认 800—1200 字，使用自然的第一人称。用户明确按已开展活动写时，可以写“通过参加此次主题团日活动，我对……有了更加深入的认识”，并结合已生成的同一活动流程反思学习收获、主题意义、校园/专业联系和后续行动。心得中如需提及日期、地点或人数，必须与其他材料一致。

可以写正常的认识变化和行动计划，不要虚构特别具体的个人经历，例如获奖、被老师单独表扬、代表发言原话或个人特殊遭遇，除非用户明确提供。用户不要求署名时，不为了署名追问个人姓名。

## 7. PPT 生成（一律使用 ppt-master 引擎）

### 7.1 引擎生成（默认路径）

**需要 PPT 时一律调用 ppt-master 引擎直接生成 `.pptx`，不把 PPT 提示词当作正常交付物。** 引擎是开源项目 ppt-master v6.4.0（MIT License，Copyright (c) 2025-2026 Hugo He），以精简归档内置在本 skill 的 `vendor/ppt-master-6.4.0.zip`（12698 个文件 / 10.28 MB）。归档相对上游裁去三类与本 skill 无关的素材——`references/ai-image-comparison/`（AI 生图风格参考图）、`templates/sounds/*.wav`（语音旁白音效）、`templates/brands/`（企业品牌素材），合计 58.72 MB；全部图标库、模板构件、脚本与文档完整保留，裁剪不影响 PPT 生成主流程。引擎是否可用由 `scripts/check_environment.py` 的「PPTX 引擎」一项确认（会校验 LICENSE 摘要），缺失与恢复办法见 [setup-guide.md](setup-guide.md)。仅当引擎或必需依赖不可用时，才按 §7.2 降级为提示词模式，并在交付报告中如实标注 PPT 未生成。

**引擎定位**：先跑自举脚本拿引擎目录，不要自行搜索或猜测位置：

```bash
python scripts/bootstrap_engine.py --json
```

脚本返回的 `engine` 字段就是本次运行的 `SKILL_DIR`。它按以下顺序处理：

| 顺序 | 位置 | 说明 |
|---|---|---|
| 1 | 环境变量 `PPT_MASTER_DIR` | 已指向有效引擎时直接使用，不解压。想让本 skill 改用外部引擎（例如本机的完整上游克隆）时设这一项 |
| 2 | 内置归档自举 | 默认路径。校验归档 SHA-256 后解压到缓存目录并复用；缓存解析顺序为 `--cache-dir` > `PPT_MASTER_CACHE_DIR` > skill 同级 `_engine/` > 当前目录 `_engine/`，候选全部落在 C 盘时脚本拒绝执行并要求显式指定 |

自举只在首次需要，之后直接复用缓存（`--check` 只报告不写盘，`--verify` 顺带跑一次引擎完整性守卫）。

**执行步骤**：

1. 把定位到的绝对路径记为 `SKILL_DIR`；后续所有命令按该绝对路径展开。ppt-master 要求把其文档中的 `skills/ppt-master/` 前缀替换为 `SKILL_DIR`，且不得 `cd`、不得依赖当前工作目录、不得假设仓库结构。定位失败时不要自行搜索或猜测引擎位置。
2. 读取 `<SKILL_DIR>/SKILL.md`，按其 Mandatory Load Order 执行（含 `attribution_guard.py` 完整性检查），选择 Generate PPTX 路线；其 BLOCKING 门控与导出流程照常执行，不跳步。完整性检查返回非零时立即停止，不检查、不修复、不绕过。
3. **内容契约优先**：传入的页面大纲必须来自事实核对卡与 output-format.md 的页面大纲规范（页数、每页字段、封面/结尾结构），主题事实、日期、地点、人数与案例一致；主题表述参考 material-library.md 对应知识卡，不得编造需要证据的数据、人物或获奖。
4. 风格基调：庄重且贴合校园场景，可使用团旗红金等共青团视觉元素；通知有明确视觉要求时以通知为准。
5. **项目目录落在交付输出目录内**：用 `init` 的 `--dir` 指定基础目录，项目会建在 `<交付输出目录>/<项目名>_<YYYYMMDD>/`，不落在引擎目录或本 skill 目录内。省略 `--dir` 时引擎默认建在引擎仓库根的 `projects/` 下（上游 .gitignore 已忽略该目录），交付件会留在引擎目录里需要手动搬出，因此始终显式传 `--dir`。

   ```bash
   python "<SKILL_DIR>/scripts/project_manager.py" init <项目名> --dir "<交付输出目录>"
   python "<SKILL_DIR>/scripts/project_manager.py" import-sources "<项目目录>" <源文件或目录...>
   python "<SKILL_DIR>/scripts/finalize_svg.py" "<项目目录>"
   python "<SKILL_DIR>/scripts/svg_to_pptx.py" "<项目目录>"          # 未启用演讲备注时追加 --no-notes
   ```

   导出成功后把 `<项目目录>/exports/` 里的 PPTX 按 output-format.md 命名复制到交付输出目录：`团日活动PPT-{支部简称}-{YYYYMMDD}.pptx`。命令逐条串行执行，上一条退出 0 再执行下一条。

   引擎内部多处使用系统临时目录（`finalize_svg.py`、`analyze_images.py`、`image_search.py` 等），执行这批命令前把 `TMPDIR`、`TEMP`、`TMP` 三个环境变量统一指向交付输出目录下的 `.tmp/`，让引擎的中间文件也落在项目目录内，不写入 C 盘。

6. **不得修改引擎的受保护文件**：`LICENSE`、`SPONSORS*.md`、`SKILL.md` 及其 frontmatter、`scripts/`、`templates/`、`references/`、`workflows/` 一律保持原样。完整性检查校验 LICENSE 摘要、SKILL.md 的身份字段与门禁标记、9 个入口脚本的 import 与调用结构，任何改动都会阻断整条 PPTX 路线。需要换引擎位置时只用 `PPT_MASTER_DIR` 环境变量，不移动、不编辑引擎内的文件。
7. 定位失败或依赖不可用时如实说明缺哪一项，按 §7.2 降级为提示词模式；不假装生成，也不改用手工拼装 PPTX 的方式绕过引擎。

### 7.2 降级：提示词模式

只在引擎不可用或必需依赖缺失时使用。输出一段可直接粘贴给 ChatGPT 网页版的提示词和页面大纲，并在交付报告里标注「引擎不可用，PPT 未生成」及缺失项。默认 10—12 页，用户指定页数时按用户要求生成，不为确认页数额外提问。页面内容随当前通知主题动态设计，不机械加入知识竞赛、情景模拟或作品展示；通知没有这些环节时，可改为案例辨析、场景判断、小组讨论、青年行动、校园实践、健康生活方式、安全知识或主题倡议等更合适的内容。PPT 必须与案例采用同一主题、日期、地点、人数和主要流程。

每页至少给出：页标题、3—5 条核心内容、建议视觉、讲解重点和演讲备注。封面通常包含主题、学院/支部和活动日期；中间页面呈现通知要求、主题理解、活动过程和行动转化；结尾回扣当前主题。不得编造人物照片、新闻出处、具体统计数据、获奖或领导评价等需要证据的结果；一般性成效可以与案例保持一致地表达。

## 8. 交付前 QA

- 原始模板未被覆盖，生成文件使用模板副本。
- **主题无关性**：规则、脚本、模板没有绑定任何具体活动主题；材料类型与前言区按结构特征识别，换主题不需要改脚本或改规则；主题表述只来自本次通知或用户。
- **环境检查**：生成前已运行 `scripts/check_environment.py`，并在交付报告中如实标注环境状态与降级项（缺依赖、未渲染、未联网核实等）。
- 案例身份行已填入真实学院全称与支部简称，未残留 `XX学院（全称）`、`XX团支部` 一类占位。
- 活动案例保留“一、活动策划；二、组织实施；（一）活动准备；（二）活动开展；（三）活动总结；三、案例点评（（一）案例推广价值、（二）思考与建议）”。
- 模板占位文本（XXXX、（模板））和排版说明注释行已替换或删除。
- 事实核对卡已输出，主题、日期、地点、人数和主要流程在核对卡、案例、总结表、心得体会和 PPT 之间保持一致；不得出现相互矛盾的活动形式或数字。
- 用户提供的真实字段、用户授权生成字段、合理补全内容和未确认信息彼此区分。
- `[待补]` 只出现在内部核对清单或独立提醒中，正式正文和正式总结表字段为空而不是写占位符。
