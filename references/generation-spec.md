# 团日活动材料生成规格

## 1. 输入解析

读取 Word 通知的正文、表格、标题和必要的文档元信息，先输出内部事实表，不要直接凭主题写全文。至少提取：

| 类别 | 要提取的内容 |
|---|---|
| 主题 | 活动主题、口号、核心价值 |
| 背景目标 | 为什么开展、面向什么问题、希望形成什么意识或行动 |
| 时间地点对象 | 实际举办日期（默认单日）、地点、参加对象、是否有分批或大班要求 |
| 形式内容 | 理论学习、观影、分享、知识竞赛、情景模拟、实践、创作等 |
| 成果要求 | 案例、总结表、心得、照片、视频/作品、命名规则、提交方式 |
| 硬性约束 | 截止时间、照片数量/格式/大小、团旗团徽团歌、审批或录入要求 |
| 缺口冲突 | 通知没有给出的表单字段，以及通知与模板之间不一致的要求 |

以“来源位置/原文要点/生成使用方式”保存关键事实。活动时间默认记录实际举办的某一天；通知中的时间段不能直接替代实际日期。时间要区分活动举办日期和材料提交时间，地点要区分活动地点和材料递交地点，不能合并成一个日期或地点。

### 1.1 生成前问询与信息分层

在生成正式 DOCX 前，先把模板中的缺失字段转成一次性问询。优先询问：举办团支部/班级简称、支部人数、参加人数、活动负责人、联系电话、活动实际举办日期（单日）；若用户明确分多天开展，再询问各日日期和对应环节。正式心得体会还询问作者姓名和班级/团支部；活动地点、过程记录和作品只在通知未明确或用户说明与通知不同时追问。即使通知写有时间范围，也必须询问用户确认具体单日日期。

通用活动案例不需要个人、工作人员、人数、电话、签到或真实效果信息，直接写主题相关、可迁移的活动方案即可。案例模板身份行严格保留 `XX学院（全称）  XX团支部（简称）` 的两段式结构；正式稿用用户回答替换占位符，缺少团支部时先问，不写 `[待补：具体团支部]`。`[待补]` 只允许出现在内部事实表或独立问询清单；用户只要预览时，可生成通用案例和空白总结表预览，并把待回答字段列入问询清单，这些字段不能混入案例正文、心得正文或正式总结表字段。

### 1.2 活动时间判定

材料中的“活动时间”默认是实际举办的某一天，不得把通知中的“X月X日至X月X日”直接照抄为活动日期。生成前固定询问：“请提供实际举办日期（单日，例如 2026年6月18日；若确实分多天开展，请说明各日日期及对应环节）。”只有用户明确确认跨天开展，或明确要求按通知时段填写，才保留时间段。确认后，活动案例、总结表、心得体会和 PPT 提示词统一使用同一日期；材料提交截止时间另列。

### 1.3 已开展活动的过程重构

用户直接要求“写活动/生成活动材料”时，默认活动已经开展，不再追问活动状态；只有用户明确要求方案、预览或说明尚未开展时，才使用“拟/建议”语气。用户只提供通知和基本信息、没有逐项过程记录时，可依据通知列明的学习、观影、讨论、竞赛、情景模拟、作品创作和总结环节，合理重构一份过去时活动过程稿。重构应保持连贯和主题相关，不添加具体奖项、个人原话、精确现场数据、照片事实或其他无法核实的证据。

本用户默认不需要照片处理，也不需要操作智慧团建、邮箱、PU 或其他提交系统：不询问、不生成/插入照片、不执行录入/上传；这些提交事项不写入活动案例、心得体会或 PPT 正文，除非用户另行明确要求。

## 2. 不同主题的通用处理提醒

每次输入的通知都可能有不同主题、学院、地点、日期和活动形式。不得把任何一次测试材料中的主题词、学校名称、活动日期、活动地点、专业方向、人物、数据或通知要求带入下一次任务；只使用当前通知和用户本次确认的信息。

通知可能同时包含活动举办安排和材料提交要求，也可能出现通知与模板对照片数量、提交方式或字段说明不一致的情况。保留内置模板结构，把冲突写入独立核对清单；不伪造照片，不把提交系统操作写入活动正文，也不把材料提交截止时间当作活动日期。

模板和排版规则已随 skill 放在 `assets/` 与 `references/layout-spec.md` 中，不需要读取外部项目。

## 3. 活动案例模板填充

保留 `活动案例模板.docx` 的“附件3”与既有章节，删除模板说明性括号，但不要删除正式章节。正文建议写成 1800—2800 字，信息密度要足够但避免重复。

身份行必须沿用模板原格式 `XX学院（全称）  XX团支部（简称）`，名称之间保留两个空格。正式稿只替换学院和团支部名称；通用预览可保留模板占位文本。案例正文不写负责人、具体工作人员、支部人数、参加人数、联系电话、签到记录或“待补”说明；这些只在用户提供后填入总结表等数据字段。

### 一、活动策划

写清通知背景、主题理解、活动目标、参与对象、内容设计、活动原则和预期效果。要把主题和学生特点、学院专业特点联系起来；可根据当前学院和专业选择合适的校园生活、专业学习或社会责任场景，但不要捏造法律条文、统计数字或具体案件。

### 二、组织实施

按模板保留以下二级标题，并用过程性细节充实：

- **（一）活动准备**：通知传达、分工、资料审核、场地/设备、团旗团徽团歌、宣传、签到和秩序安排。未给出的负责人或人数使用待补项。
- **（二）活动开展**：覆盖通知列明的主题学习、观看/阅读材料后的讨论、知识竞赛或情景模拟、与主题和专业相关的校园场景、作品创作/展示。为每个环节写目标、参与方式、讨论问题和预期产出；实际未发生的环节使用“拟/建议”。
- **（三）活动总结**：分别写认识收获、行动转化、支部氛围、材料成果、后续计划。只有获得真实数据后才写“共有 X 人参加”“现场反响热烈”等事实句。

### 三、案例点评

写案例推广价值、与专业学习/校园生活的结合、可复制方法、亮点、不足和改进建议。不能只重复活动流程，要解释“为什么有效、如何迁移、下一次怎样改进”。

案例正文的内容边界：通知或模板中的提交方式、截止时间、照片数量、文件命名、材料核对、待补信息和来源冲突不得写入活动叙事、活动总结或案例点评。它们应放入总结表备注或单独的“待补信息与冲突核对清单”。案例点评要评论活动本身，例如环节之间是否形成递进、讨论是否连接学院专业与校园生活、情景模拟是否要求成员解释判断依据、作品任务能否转化为具体行动；若活动尚未实际开展，应使用“从方案设计看/拟”而不写现场成效。

## 4. 总结表字段映射

不改变合并单元格和表格几何，仅填入对应位置：

| 表格字段 | 写入内容 |
|---|---|
| 学院名称 | 通知中的学院全称 |
| 举办支部 | 用户提供的具体团支部/班级；正式生成前缺少则先询问，预览时保留空白 |
| 活动名称 | `主题 + 主题团日活动`，与通知保持一致 |
| 活动时间/地点 | 用户确认的实际举办日期（默认单日）和地点；如果是拟定方案，标明“拟” |
| 支部人数/参加人数 | 只用用户提供的真实数字；正式生成前缺少则先询问，预览时保留空白 |
| 活动负责人/联系电话 | 只用用户提供的真实信息；正式生成前缺少则先询问，预览时保留空白 |
| 活动过程及效果 | 约 600—900 字的压缩版过程与效果；不要把案例全文塞进单元格 |
| 学院团委意见 | 保留空白、盖章和日期位置，不代填意见或印章 |
| 备注 | 仅写必要的待补项、材料提交说明或冲突提示 |

本用户默认不处理照片，不生成、下载、插入或管理照片；如果用户另行明确要求照片处理，再单独确认范围和真实素材来源。

## 5. 心得体会/读后感

默认写 800—1200 字，采用团员青年第一人称但不虚构个人经历。结构为：

1. 阅读通知或学习主题后的第一层认识；
2. 对主题核心问题、青年责任和现实意义的理解；
3. 与当前学院专业、校园生活和个人日常行为的联系；
4. 由“知道”转向“会做”的具体行动，如辨别风险、遵守规范、主动互助、理性选择或积极宣传；
5. 结尾回扣本次活动主题，给出可执行的承诺。

如果用户要求“活动后心得”，必须先确认活动已经开展；否则标题和语气使用“阅读通知后的心得/学习体会”，不要假写现场体验、发言或集体成果。

## 6. PPT 生成提示词大纲

输出一段可以直接粘贴给 ChatGPT 网页版的完整提示词，随后给出 10—12 页的页面大纲。默认设定：中文、16:9、面向当前学院和团员青年、庄重而有青春感、主色根据主题选择、结合通知主题的视觉元素、每页少量核心句并配讲解备注；活动日期必须使用用户确认的实际单日日期，不得把通知时间段自动写入 PPT；日期未确认时先询问，不生成正式提示词；不得编造统计数据、案例出处、人物照片或活动结果。

推荐页面顺序：

1. 封面：主题、学院/支部、日期；
2. 为什么本次主题与青年有关；
3. 主题核心概念和现实问题；
4. 主题与校园生活、专业学习的联系；
5. 通知要求与本次活动目标；
6. 学习/观影/讨论环节；
7. 知识竞赛与情景模拟环节；
8. 当前学院专业学生的责任与行动；
9. 作品创作、展示或成果占位；
10. 从课堂到日常的行动清单；
11. 支部共建与后续计划；
12. 结语：回扣本次活动主题，提出青年行动承诺。

每页大纲至少给出：页标题、3—5 条核心内容、建议视觉、讲解重点、需要用户补充的事实。PPT 提示词是交付物，不是 PPT 文件；除非用户另外要求，不调用 PPT 生成器或直接制作演示文稿。

## 7. 排版与 QA

以内置的两个活动模板和 `references/layout-spec.md` 为第一版式来源：A4 纵向、模板既有页边距、宋体/黑体层级、正文四号、固定 25 磅、首行缩进两字符和表格几何都应保持稳定。对新建心得体会，可沿用案例模板的标题/正文层级；不要加入与团日活动无关的论文封面、摘要、目录、公式或参考文献。

依据内置排版规范做排版检查：显式设置字体、字号、间距和标题层级；不使用手打伪标题或伪列表；避免表格溢出、单元格文字贴边、标题孤行和大面积空白。每次 DOCX 修改后渲染为 PNG，逐页检查中文字体、表格、分页和占位符；渲染不可用时做结构审计并说明。

## 8. 交付前核对表

- [ ] 文件是模板副本，原始模板未被覆盖。
- [ ] 主题、学校、学院、时间、地点、对象与通知一致。
- [ ] 活动举办时间和材料提交截止时间没有混淆。
- [ ] 已发生事实、建议内容和待补信息有明确区分。
- [ ] 活动案例正文没有混入通知提交要求、照片数量、模板说明、待补说明或冲突核对等材料管理话语。
- [ ] 人数、姓名、电话、照片、盖章和效果数据没有被编造。
- [ ] 活动案例、总结表、心得体会和 PPT 提示词用途没有混写。
- [ ] 通知与模板冲突已列出并给出处理口径。
- [ ] DOCX 版式已渲染检查，输出文件名不含 Windows 非法字符。
